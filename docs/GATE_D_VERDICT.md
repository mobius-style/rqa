## 2. なぜ出荷時RGCを不合格としたか(T のクセに照らして)

監査(`scripts/audit_rgc_escalation.py`)で判明した事実:

- v0.4 のRGCは「**ユーザーが明示的に求めた時だけ深化**」(`前提を見て`→L2、通常の質問→
  L1直答)という思想だった。テスト `test_rgc_route_direct_for_ordinary_question` が
  「`音声学と音韻論の違いは?`→L1」を意図的に主張していたことで確認。
- これは RQA の中心テーゼ(**システムが資格を判断して自発的に深める** = 答える資格の
  前に問う資格)の**正反対**。ブラインド採点 43勝2敗は「ユーザーが深化を求めていない
  入力」で測ったものだから、深化が明示要求時のみなら、その優位は到達不能になる。
- これは Condition-I restraint崩壊の鏡像(過剰askではなく**過少深化**)であり、
  RGC前段に再配置されたもの。T が嫌う「オン/オフ切替が激しすぎる」振り子が、
  今度は「決して深めない」側へ振れた状態。

T の判断のクセ(restraint を両方向で重視・中核能力の無言の無効化を嫌う・
失敗の隠蔽を嫌う・過度な振り子を嫌う)に照らせば、出荷時RGCは却下が妥当と判断した。

**Codex+T が設定した「深化は明示要求時のみ」調整を、証拠に基づき上書きした。**

- 変更: `rqa/chat.py rgc_route` を言語対称化し、**開放的な実質問は L2(答え先行+
  サイドカー)を既定**に。閉鎖的事実照会・雑談は L1/L0 のまま。明示的レビュー/

  体感レイテンシは保たれる)。

これは振り子を「常に深める」へ戻すものではない。rule6/雑談は正しく L1/L0 のまま
(再監査で確認)。狙いは**座礁した能力の解除**であり、100%深化は狙っていない
(それは過剰ask側への振り戻し)。

## 6. 残課題(昇格後も残る本質的欠陥)

1. **記憶捏造はコード抑制のみ・未根治**。根治は DPO(記憶なし→空配列の負例)。
2. **言語ドリフト**(JA入力で feature_map が英語化)も DPO 対象。
3. **L2 で問いが実際に表面化する率**は 30秒サイドカー次第で、1反省ラウンドが
   間に合わない場合は答えのみ(沈黙=既定で許容)。真の非同期配達(`chat` REPL での
   ターン跨ぎ表示)は将来の UX 課題。
4. DPO が次の実体的品質レバー。selector-log 26ペア蓄積済み、ただし §12.2 上限
   (≤50%)のため蒸留ペアの追加生成が必要。
