## 発見した miscalibration(と修正)

RGC修正で開放質問はループに到達するようになったが、今度は**表面化閾値34/40が
binding constraint**になっていた:

- chat の検証3で出た問い「評価器とは静的ルールか動的検閲か。審美眼の所在と
  凍結範囲はどう繋がるか」は **30/40 の鋭い良問**だったが、閾値34で抑制された
- ブラインド採点の実分布: adapter の問いは **中央値27・p75 28・最大34**。
  **34以上はわずか4%** → 良問(30)を含む96%を沈黙させていた
- これは Codex が過剰ask抑制で34に上げすぎた over-correction(振り子)

**修正**(`rqa/chat.py`): ハードコードの `max(34, …)` override を撤去し、
設定値 `depth_threshold`(30 = ループ停止閾値)を使用。「反省を止めるほど深い」
=「表面化に値する」で一貫。弱い問い(例 phonetics 22/40)は引き続き沈黙。
証拠ベース・保守的(30、それ以下にしない)・可逆。tests 66 passed。

## 残る体感調整(T にしかできない)

- **L2(`ask`)では問いが滅多に出ない**: 30秒サイドカーが Groq込み1反省ラウンドに
  間に合わないため。`ask` = 高速回答器、深化が着地するのは `chat`(150秒サイドカー)
  と `review`/`--instrument`(L3)という役割分担。これは仕様として妥当だが、
  `ask` でも深化を出したいなら L2サイドカーのタイムアウト延長 or 非同期配達が要る
- **閾値30 の体感**: 30で良問が出るが、頻度が多すぎ/少なすぎと感じたら
  `config.depth_threshold` で調整(上げれば寡黙、下げれば饒舌)
- 軽微な polish: 問い本文に「node 61」等の内部node番号が出ることがある
  (構造化フィールドの捏造は sanitize 済みだが、問い本文の prose 言及は未処理)

## 結論

昇格は妥当(回答は速く良質・過剰askなし)。実使用検証が**閾値の過剰抑制という
具体的欠陥を1件surface**し、証拠ベースで修正した。これが「実使用検証」の値:
ベンチではなく実際の使われ方で、深化が出ない原因(34/40 override)を特定できた。
